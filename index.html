Abstract

Computer-use agents now run tasks from everyday desktop work to long professional workflows. Most agent interfaces use screenshots with mouse and keyboard input. Because of this design, the model must interpret pixels at every step, while the semantic and programmatic interfaces of the computer stay hidden.

We introduce Hybrid Computer Use (HCU). HCU combines three channels in one interface: code and command-line tools, accessibility (AX), and the GUI. HCU is a two-tool MCP server (AX and GUI) that runs beside the agent's own shell and file tools. It returns compact AX working trees with short refs (aN → wN → rN), runs batches of actions with in-call waits, reports post-action AX diffs, and checks live state before it sends any desktop input.

On OSWorld 2.0, OSWorld 1.0 (five frontier models, four harnesses), WeaveBench, MacAgentBench, and Windows Agent Arena, HCU raises task scores and lowers cost.

What HCU adds

  • AXGUITwo MCP tools, AX and GUI, next to the agent's own shell and file tools.
  • a1›w1›r12Short refs such as a1 → w1 → r12 that stay bound to one window.
  • Batches of up to 64 actions with in-call waits and a diff.
  • r13✓x,y✓Guards that check the target and the layout before any input.
  • One Go core with native providers for Linux, macOS, and Windows.

Computer use belongs inside a general agent

Benchmark agents usually run a separate screenshot loop. Production agents such as Codex and Claude Code already have code tools, caching, and skills. HCU adds the computer to that agent instead of building a new loop.

Keep the context stable

A screenshot loop sends a 1080p image (about 2.4K tokens) at every step and drops old images. Each drop changes the prompt prefix, so the prompt cache stops working. Inside an append-only agent harness, earlier model turns stay cached.

Act on semantics, not only pixels

AT-SPI, AXUIElement, and UI Automation describe each window as a tree of controls with roles, values, states, and actions. Products already act through this tree, but OS benchmark baselines mostly used it only to observe.

Shared desktop4 calls
Own computer1 call

Give the agent its own computer

Drivers built for a shared human desktop must act in the background. Background execution rejects many actions and allows only one action per call. A dedicated computer lets the interface favor speed and reliability.

Three channels, one desktop

HCU adds two MCP tools, AX and GUI, next to the agent's own code tools. All three channels change the same desktop, so HCU checks live state before every input.

Programmatic

Code

Edit files, query databases, and run CLI tools directly. This channel is the agent's native shell; HCU does not wrap it.

bashpythonfile edit

Shared state. Code changes are visible to the next AX or GUI call.

Semantic

AX

Read a compact control tree, find elements, and run a batch of up to 64 actions on short refs, with in-call waits. Each batch reports a diff.

appsobservefindact

Target guard. HCU resolves every ref again against the live tree and its window before input.

Visual

GUI

See the full desktop at 1366 × 768, zoom into small text, and click, drag, scroll, and type in one batch. Use GUI for canvases, images, and controls that AX cannot read.

screenshotzoomactions[]

Layout guard. Coordinates belong to the last screenshot. If the window under a point moved, closed, or was covered, HCU sends no input and returns a fresh screenshot.

One AX call, from tree to diff

In a typical AX action call, the model sends one batch. HCU resolves the refs, dispatches the actions, waits, and reports the change in the same round trip.

1Project the tree

HCU reads the accessibility tree (169 nodes for Chrome settings) and shows the model a 73-line view that keeps every control the model can act on.

Before each step, HCU resolves the ref against the live tree and its window, sends the native action, and waits until the page stops changing.

    Where the gains come from
    
          
    Every model scores higher with HCU, and each divides work across the channels differently. Nearly all of the gain comes from tasks where HCU makes at least one AX or GUI request.

On 29% to 31% of the tasks where GPT-5.4, Gemini 3.8 Flash, or Grok 4.7 used GUI, every GUI request was a screenshot and every action went through AX.

      GUI, AX, and ordinary code in one program. AX state becomes variables to loop and branch on. Screenshots from pyautogui stay in the program; only the result returns to the model.
      
            
      import pyautogui as gui
from pytesseract import image_to_string as ocr

def receipt_total(row):         # reused per row
    # GUI: the pixels stay in the program
    gui.doubleClick(row.thumb.center)
    img = gui.screenshot(region=ax.bounds("w2"))
    gui.press("esc")
    return money(ocr(img))

for row in ax.rows("w1", status="Pending"):
    claimed = money(row.text)   # AX: text
    match = receipt_total(row) == claimed
    name = "Approve" if match else "Flag"
    ax.click(row.button(name))  # AX: by ref

assert not ax.rows("w1", status="Pending")
print(ax.diff("w1"))  # 11 approved, 3 flagged
